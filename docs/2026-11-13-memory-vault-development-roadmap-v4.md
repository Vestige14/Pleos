# 기억 저장소 초기 구축·개발 순서 및 브랜치 운영 v4

작성일: 2026-11-13 (Asia/Seoul)
상태: 개발 착수 전 일정·운영 계획. 구현·빌드·에뮬레이터 설치·API 호출·커밋·push는 이 문서 작성 과정에서 수행하지 않았다.

## 기준과 승인 범위

사용자는 기존 코드가 없는 초기 세팅부터 개발하며, 앞서 지적한 정정 사항을 반영해 진행하도록 요청했다. 단계마다 브랜치를 만들고 릴리즈마다 버전 브랜치를 유지한다. 기존 원본 문서는 변경하지 않는다.

- 제품 범위: 원본 PRD 및 `2026-11-13-memory-vault-demo-v2.md`.
- OpenAI 변경: `2026-11-13-memory-vault-demo-v3-openai-offline-addon.md`.
- 이 문서: 위 문서의 정정 사항, 실행 순서, 예상 시간, 브랜치 운영을 통합한다.
- 사용자 직접 요청 > 이 문서의 정정 > v3 추가 설계 > v2 > v1 순서로 충돌을 해소한다. 원본 PRD의 필수 기능은 임의 삭제하지 않는다.
- 로컬 작업 대상은 채팅에 등록된 Pleos 경로다. 현재 경로가 열리지 않으므로 초기 세팅 때 경로와 상위 디렉터리를 확인하고 빈 프로젝트를 준비한다. 기존 저장소가 발견되면 먼저 상태를 확인하고 보존한다.
- 원격 대상은 `https://github.com/chowonbhin/Pleos.git`. 원격 상태를 먼저 확인하고 기존 이력을 덮어쓰지 않는다.
- 현재 문서 작성에는 subagent를 사용하지 않았다. 실행 시 사용자 지정 모델·추론·서비스 설정을 실제 도구가 지원하는지 확인하며 지원되지 않으면 임의 대체하지 않는다.

## 개발 순서와 예상 시간

시간은 초기 구축부터 테스트·수정·통합을 포함한 집중 작업량 추정이다. 완료 시각이나 자동 실행 속도를 보장하지 않는다. 다운로드, 계정 설정, 사용자의 마이크 발화 확인, 승인 대기는 별도다. 기존 계획의 11/15 21시 목표 달성 여부는 초기 실험 후 다시 판단한다.

**합계 18~27시간.** 환경·SDK·마이크·API 문제 대응 여유 3~5시간을 포함하면 **21~32시간**을 확보하는 것이 계획상 안전하다. 앞선 6~10시간은 OpenAI 추가분의 추정이었으며 전체 개발 시간이 아니다. 2단계 후 실제 빌드·음성·차량 상태 결과에 따라 잔여 시간을 재산정한다. 일정이 부족하더라도 음성 기능을 텍스트 입력으로 몰래 대체하거나 필수 검증을 생략하지 않는다.

1~2단계는 기능 가능성 확인이다. 이후 각 단계는 실행 앱·PNG·실제 API 응답 등 검사 가능한 결과물을 제공한다. 테스트 로그만으로 단계 결과를 대신하지 않는다. 구현은 한 번에 한 작업씩 진행하고 완료 검토 후 다음 작업으로 간다.

## 브랜치 및 릴리즈 운영

| 브랜치 | 역할 |
| --- | --- |
| `main` | 검증된 데모 기준선. 초기에는 프로젝트 시작점이며, 릴리즈 통합 이후 검증 버전을 가리킨다. |
| `develop` | 순차 개발 통합 브랜치. 다음 단계는 검증된 develop에서 시작한다. |
| `feature/01-...` ~ `feature/08-...` | 위 표의 단계별 작업. 해당 단계 변경만 커밋하고 검증 후 develop에 로컬 통합한다. |
| `release-v0.1.0` | 3단계 완료: 오프라인 방문·메모 저장, 재시작 복원. |
| `release-v0.2.0` | 5단계 완료: 사진 연결과 공유 PNG까지 동작. |
| `release-v0.3.0` | 7단계 완료: 실제 OpenAI 연결과 사용자 검토까지 동작. |
| `release-v0.4.0` | 8단계 완료: 검증 및 시연 준비를 마친 최종 데모. 실제 차량 상용 배포 인증을 뜻하지 않는다. |

운영 규칙:

1. 단계 브랜치는 직전 단계가 검증·통합된 develop에서 만든다. 동시에 여러 구현 브랜치를 변경하지 않는다.
2. 릴리즈는 해당 기능의 실제 실행 검증을 통과한 통합 커밋에서 만든다. 실패·미완료 빌드에는 릴리즈 버전을 붙이지 않는다.
3. 최종화된 release 브랜치는 후속 개발로 이동시키지 않는다. 동일 커밋에 `v0.x.0` 로컬 태그를 만들어 기준점을 고정한다. Android versionName도 릴리즈 버전과 맞추고 versionCode는 증가시킨다.
4. 릴리즈 후 수정이 필요하면 해당 릴리즈에서 `fix/v0.x.1-설명` 브랜치를 만들고 검증한 새 `release-v0.x.1`과 태그를 만든다. 수정 사항은 develop과 필요한 기준선에 반영한다. 기존 릴리즈·태그를 덮어쓰지 않는다.
5. 로컬 단계 통합과 버전 관리는 요청한 개발 흐름에 포함한다. 원격 push, GitHub Release 게시, 배포·제출은 각각 명시적으로 승인된 범위에서만 수행한다. 릴리즈 브랜치 생성이 공개 게시를 뜻하지 않는다.
6. 기존 원격 브랜치/태그가 있다면 이름과 이력을 먼저 확인한다. 충돌하는 이름을 삭제·강제 이동하거나 force push하지 않는다.

## 검증 및 진행 방식

- 초기 플랫폼 실험은 제한된 프로토타입으로 수행한다. 본 구현은 해당하는 TDD 절차를 적용한다.
- 초기 실험, 각 실행 가능한 단계, 릴리즈에서 결과물·실행 방법·검증 증거·남은 문제를 전달한다. 일반 단계마다 재승인을 요청하지 않는다.
- 오프라인 저장, 프로세스 재시작, 권한 변화, 주행 상태 전환, 늦은 API 결과, 서버 장애를 각 소유 작업의 테스트에 포함한다.
- 실제 OpenAI 키는 서버의 로컬 환경/비밀 저장소에만 둔다. 실제 API 검증에는 사용 가능한 키·모델·비용 한도가 필요하며 이를 채팅이나 Git에 기록하지 않는다. 준비 전에도 fake 서버로 다른 개발은 진행한다.
- 보존해야 할 기존 코드·자료가 나타나면 덮어쓰지 않는다. 범위를 바꾸는 결정·유료 서비스/외부 공개 등 기존 승인 밖 행동은 분리한다.
- P1 사진 이동·배지 확장·문장 다듬기·3D는 위 일정에 포함하지 않는다. 방문은 시드 시연 데이터이며 실시간 방문 감지는 범위 밖이다.

## 완료 기준

새 Pleos AVD에서 방문 초안 → 사진/메모 확인 → 공유 선택 → 개인정보가 제외된 PNG 내보내기가 동작한다. 오프라인 음성 원문이 보존되고 연결 후 실제 OpenAI가 저장된 방문을 근거로 제안한다. 사용자의 연결 수정은 늦은 응답으로 덮어쓰지 않는다. 각 릴리즈의 브랜치·태그·APK·검증 기록이 같은 소스 상태를 가리킨다.
