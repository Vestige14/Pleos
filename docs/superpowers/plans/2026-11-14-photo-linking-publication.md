# 4단계 사진 feature 게시 계획과 수락 범위

기준 main: `21cbd4cb0dd83bfbb2519fd5aaba621b32ad5a5f`. 사용자의 2026-11-14 후속 지시에 따라 사진 기능만 `feature/04-photo-linking`으로 분리해 게시하고, 로컬 main에 병합·검증한 뒤 origin/main을 최신화한다. 5·6단계의 공유/백엔드 준비 코드는 기존 병렬 작업 공간에 보존하며 이번 브랜치에 포함하지 않는다. 릴리즈/태그/후속 단계 착수는 승인 범위가 아니다.

## 수락 정정

- 사진 권한의 실제 수락 범위는 **전체 사진 허용·거부·철회·재부여**로 정한다. 선택 사진/GPS만 독립 변경하는 OS 조합은 이번 완료 조건에서 제외한다. 기존 관련 로직을 제거하지 않으며 실제 미검증을 명시한다.
- 기존 UI 자동 검사의 간헐 노드 부재·NoRoot·idle timeout은 [이슈 #2](https://github.com/chowonbhin/Pleos/issues/2)로 유지하고, 이번 사진 feature 게시/main 반영을 차단하지 않는다. 실패한 결과를 성공으로 바꾸거나 테스트를 삭제/skip/완화하지 않는다. 새 독립 결함까지 포괄적으로 면제한 것은 아니다.
- 임시 진단 helper/wrapper는 원문 해시 대조 후 복원했다. 제품 사진 로직·기존 안전 gate·마이크 권한은 진단 목적으로 바꾸지 않는다.

## 구현·검증·게시 순서

1. 최신 main을 `pull --ff-only`로 확인하고 별도 사진 feature 작업 트리를 만든다. 검토 완료 사진 37파일을 해시 대조해 옮기며 사용자·다른 작업자의 변경을 보존한다.
2. 사진 후보/EXIF, 비파괴 Room migration, 사용자 결정 보존, foreground/PARKED/generation thumbnail 취소의 검토·RED/GREEN 근거를 대조한다. 실제 전체 사진 권한·후보·확정/해제·재스캔·프로세스 재실행·D/UNKNOWN 숨김 결과를 기록한다.
3. 사진 전용 소스에서 JVM/Lint/제품·테스트 APK 및 기기 검사를 실행하고 결과를 사실대로 기록한다. 주차/전용 기기/마이크 미사용 조건을 유지한다. 원래 78개 조사에는 공유13개가 포함됐으며 이 브랜치의 기기 전체는65개다.
4. 신선한 독립 whole-branch review를 받는다. 구현자는 자신의 작업을 최종 독립 승인하지 않는다. reviewer는 source/index/Git/기기/빌드 쓰기 권한이 없다.
5. 인수인계·실행 문서와 이슈 연결을 확정하고 working/staged/tracked 파일, 전송 이력/blob, 산출물의 비밀정보를 검사한다. 값은 로그에 출력하지 않는다. 소스/문서만 로컬 커밋한다.
6. 정확한 remote/branch/commit 범위를 확인해 승인된 feature를 먼저 push한다. 로컬 main을 다시 최신화한 뒤 feature를 로컬 병합하고 병합 결과를 검증한다. 인수인계·비밀정보 점검 유효성을 확인하고 origin/main을 push한다. force push, 사용자 변경 reset/stash, 다른 브랜치 삭제는 하지 않는다.
7. feature/main/이슈 링크·실제 검증 결과·알려진 한계를 보고하고 중단한다. 기존 병렬 계획의 임시 자료는 미완료 작업이 남아 있으므로 보존한다. 이 게시 계획의 임시 자료만 clean review 및 필요한 수정 통합 뒤 정리한다.

## 판단 기록

- Ruling: 사진37파일을 검토 완료 해시 그대로 별도 feature에 분리 — 사용자가 4단계 feature 게시를 요청했고 공유/백엔드는 별도 준비물 — 잘못 판단하면 후속 브랜치에서 사진 기반 재통합 작업이 필요하다.
- Ruling: 전체 사진 권한만 이번 실제 수락 범위로 확정 — 사용자 명시 정정과 현재 Pleos OS의 허용/거부 UI — 잘못 판단하면 선택 사진/GPS 독립 권한을 제공하는 환경에서 별도 검증이 필요하다.
- Ruling: 알려진 UI 간헐 실패는 이슈 #2를 열어 둔 채 게시 — 사용자 명시 승인 — 잘못 판단하면 자동 회귀의 신뢰도가 제한되므로 이후 수정을 별도 추적해야 한다. 새 결함에는 이 면제를 확대하지 않는다.
- Ruling: main을 로컬에서 병합·검증한 뒤 원격 반영 — 사용자 추가 승인 및 저장소 Git 규칙 — 잘못 판단하면 최종 검증 비용이 추가되지만 원격에 미검증 병합을 먼저 올리지 않는다.

## 이후 사용자 정정

최종 검토 중 사용자가 오늘 5단계→UI 수정→6·7단계→8단계 촬영 준비까지 이어서 진행하도록 지시했다. 이 문서의 후속 단계 중단은 이번 사진 게시 범위 설명이며 새 후속 실행 지시를 막지 않는다. 각 기능의 별도 외부 게시·비용/권한 승인 경계는 유지한다.

최신 정정: 사용자가 feature에 단계 번호를 붙이고 main push 후 중지하도록 지시했다. 최종 `feature/04-photo-linking`과 main만 게시 완료 확인 후 중단한다. 이전 `feature/photo-linking`은 보존하며 다음 단계는 재개 지시를 기다린다.

- Ruling: main 최종 회차 PhotoReviewScreenTest72행의 NoRoot를 이슈 #2로 함께 보류 — 상태변경·stale callback 검사 전에 root가 없어 기존 간헐 유형과 일치하며 사용자 보류 승인 적용 — 잘못 판단하면 사진 UI에 기여한 별도 원인이 늦게 발견될 수 있으므로 새 실패 위치·64/65 결과를 남긴다.
