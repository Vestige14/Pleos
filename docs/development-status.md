주행/UNKNOWN/foreground/generation 안전 제한, 선택·공개 PNG·영수증 보존은 유지한다. 공유창 또는 수신 앱의 실제 Activity 전환과 URI 접근을 조사하고 원인에 맞는 최소 수정·회귀·실제 전달 검증을 수행한다. 공유 기능 검증을 위해 개인 계정/타인에게 전송하거나 계정 로그인·외부 게시를 자동 진행하지 않는다. 합성 PNG와 로컬 수신 흐름으로 먼저 검증한다. 6단계 수정 재검토는 독립 진행하며 원본 음성/STT/선택적 위치 저장 계약과7단계 의미 연결 이관은 그대로다.

## 2026-11-14 최신 저장 계약 — 캡처 위치는 선택 정보

사용자: “6단계의 녹음 당시 위치는 못얻을 상황이면 그냥 위치 정보 없음으로 저장해도 돼”. 녹음 당시 유효한 위치를 얻지 못하면 위치 정보 없음으로 저장하며 원본 음성·STT 텍스트 저장을 위치 확보 때문에 실패시키거나 계속 대기시키지 않는다. 권한 거부·제공자 미지원/오류·시간 내 응답 없음·유효성/신선도 기준 미충족은 위치 없음으로 처리할 수 있다. 오래된 위치·시드 좌표·내비 목적지를 현재 캡처 위치로 대신 넣지 않는다. 실제 누락은 null/명시적 없음으로 구분하며 (0,0)을 누락 표시로 쓰지 않는다.

이 결정은 위치 취득 가능 경로의 구현·검증을 생략한다는 뜻이 아니다. 유효한 위치가 제공되면 출처·시각 계약에 따라 저장하고, 제공되지 않는 경로에서도 음성/STT 기록이 보존되는지 검증한다. 권한을 우회하거나 주행 중 권한창을 띄우지 않는다. 기존 차량 속도/주행 상태의 안전 잠금은 캡처 위치의 선택 여부와 별개이며 그대로 유지한다. 이 저장 계약은 확정됐지만 원본 음성·위치 저장 구현 완료를 뜻하지 않는다.

Ruling: 캡처 위치 부재를 음성/STT 저장의 차단 조건에서 제외한다 — 사용자가 위치 없음 저장을 명시적으로 허용했다 — 후속 연결의 단서가 줄 수 있으므로 누락을 실제 좌표로 가장하지 않고 7단계에서도 위치 없이 처리한다.

## 2026-11-14 최신 단계 경계 — 6단계 기반 우선 · 기억 연결 확장은 7단계

사용자가 “그 ai 연결은 7단계에서 해도 되지 않나?”에 이어 “6번은 그렇게 해. 7단계로 미룰것만 미루고 6단계에서 해야할 거는 하고”라고 승인했다. 아래 과거 절보다 이 경계를 우선한다.

- **6단계:** 기존 AI 통신·인증·대기열·재시도·응답 저장과 사용자 확정 보호를 안정화한다. 독립 검토 I1/M1 수정, 실제 API 합성 시나리오·사용량 수락을 유지한다. 원본 음성 + STT 텍스트 + 캡처 위치를 보존하는 수집·저장 기반도 누락하지 않는다. 플랫폼 조사 결과를 바탕으로 실제 입력 가능성·실패 처리·보존 계약을 정리해 검증하며, 조사만으로 구현 완료를 선언하지 않는다.
- **7단계:** 사진 내용 해석 및 저장된 사진·내비 목적지·다른 음성 기억 간의 의미 기반 연결을 확장하고 사용자의 확인·수정·해제를 구현한다. 근거가 없으면 연결하지 않고 원본 기록만 유지한다. 기존 시간/GPS 사진 후보와 현재 텍스트→방문 연결은 보존하며, 새 다중 기억 해석을 6단계 완료 조건으로 추가하지 않는다.
- 내비 최근 목적지 조회는 공식 계약이 있지만 방문 시각 필드가 없으므로 날짜 있는 방문 이력으로 가장하지 않는다. 6단계의 캡처 위치 저장과 7단계의 내비 근거 활용을 구분한다.
- 원본 음성은 현재 미구현이다. 기존 STT request의 원음 반환은 확인되지 않았고, 단일 AudioRecord의 PCM을 로컬 파일과 ON_DEVICE sendAudio에 함께 전달하는 경로가 검증 후보다. 실제 기기 성공·마이크 시험은 아직 없으며 실제 발화 시점은 사용자와 조율한다. 사진/원음 외부 업로드, 상시 위치 수집, 자동 모델 대체는 이 결정으로 추가하지 않는다.
- 5단계 최종 검증은 계속한다. 7단계 착수·전체 UI 다듬기·원격 push·Release는 현재 진행 범위에 포함하지 않는다. UI 다듬기는 기존 결정대로 P2/3D 기억 맵 때 진행한다.

Ruling: 사진 내용 기반 다중 기억 연결은 7단계로 이관하고 6단계 통신·검증 및 수집/저장 기반은 유지한다 — 최신 사용자 승인과 기능 의존성에 맞춰 6단계 범위의 불필요한 확대를 막는다 — 저장/연결 계약을 잘못 나누면 7단계 데이터 구조·API 재작업이 생길 수 있어 연결 확장을 고려한 식별자·출처·시각 계약은 구현 전에 정리한다.

## 2026-11-14 실행 재개 — 5단계 검증과 6단계 변경 준비 병행

사용자가 “6단계도 진행해 바로”라고 명시하여 직전 6단계 보류를 해제했다. 5단계 독립 재검토/수락은 계속하고, 6단계는 기존 구현의 독립 검토 결함 수정과 확정된 새 기억 처리 요구의 플랫폼 조사·설계/계획 정리를 재개한다. 원본 음성+STT+위치 보존 및 기존 사진/내비 목적지/다른 음성 기억과의 근거 기반 연결을 목표로 한다. 연결할 기록이 없으면 저장만 유지한다.

기존 6단계 snapshot을 보존하고 재사용 가능한 대기열/재시도/인증/사용량 통제는 유지한다. 기존 API에 사진·음성을 몰래 추가하거나 원본 녹음과 STT 동시 확보·내비 과거 이력 접근이 가능하다고 가정하지 않는다. 실제 플랫폼 근거에 맞춘 변경 설계와 데이터/전송 계약을 정리한 뒤 의존 구현을 진행한다. 원격 push·Release·실제 마이크 시험 시점 및 승인된 누적 API 한도는 기존 경계를 유지한다.

## 2026-11-14 최신 요구 확정 — 원본 음성 보존과 기억 간 연결

사용자는 “해변에서의 노을이 좋았어”라는 기록을 예로 다음 동작을 명시했다. 원본 음성 + STT 텍스트 + 위치 데이터를 저장하고, AI는 이미 저장된 기억에서 관련 노을 사진·내비게이션 목적지 기록·다른 음성 기록 등이 있으면 연결한다. 관련 근거가 없으면 연결을 억지로 만들지 않고 기록만 저장한다. TTS가 아니라 **원본 음성 + STT 텍스트 저장**임을 추가 답변으로 확정했다. 이는 방문 추천이나 대화형 질문 생성에 대한 요구가 아니다.

이 요구는 기존 v3의 같은 날짜 방문 후보에 메모를 묶는 범위와 원본 음성 미보관 정책을 확장·정정한다. 현재 제품은 STT 텍스트만 저장하며 원본 음성 보존·사진 내용 기반 기억 연결·내비 목적지 이력 수집·기억 간 연결을 구현 완료했다고 볼 수 없다. 기존 구현과 원문 자료는 보존한다.

현재 실행 순서는 **5단계 확인 우선, 6단계 실행 보류**를 유지한다. 6단계 재개 전 원본 음성 수집/저장, 위치·내비 기록 확보, 기억 및 연결 데이터 구조, 사진/음성 해석과 전송 범위, 사용자 확인 방식 및 검증 계획을 새 요구에 맞춰 정리한다. 로컬 저장 요구를 모든 원본의 자동 외부 업로드 승인으로 해석하지 않는다. 실제 SDK/API의 데이터 제공 가능성은 확인 전 가정하지 않는다. 이번 요구 확정만으로 마이크 시험·6단계 구현 재개·7/8 착수·push를 실행하지 않는다.

## 2026-11-14 모델 선택 — 앱 기본 Terra

사용자는 6단계뿐 아니라 7·8단계와 후속 P1·P2까지 고려해 앱 기본 모델을 `gpt-6.1-terra`, 초기 `reasoning.effort`를 `low`, API 처리를 Standard로 정했다. 개발 에이전트 모델/추론 설정과 별개다. 실제 계정 접근·한국어 정확성·지연·사용량 검증은 아직 남았다.

- 현재는 메모 텍스트와 최소 방문 후보만 전송한다. 원본 음성은 ON_DEVICE STT로 텍스트화하며 사진 전송을 이번 결정으로 추가하지 않는다.
- P1 문장 다듬기와 향후 별도 설계할 사진·메모 통합 해석에서도 Terra를 우선 평가한다. P2 3D 맵 렌더링은 앱이 담당하고, 향후 분석 결과는 저장·재사용하며 입력 변경 시 필요한 부분만 갱신하는 방향이다.
- Sol은 Terra의 반복 실패 유형이 확인될 때 별도 비교 평가하는 후보이며 자동 fallback을 추가하지 않는다. 촬영에는 품질 검증을 통과한 모델/설정을 고정한다.
- 실행 모델·추론 설정은 서버 로컬 환경에서 공급한다. 키·예산·가격·실사용 금액은 추적 문서에 넣지 않는다. 누적 비용 제한과 실제 API 호출의 총괄 소유권을 유지한다.

내비 전환 후에도 명시적으로 시작한 녹음을 계속하려면 세션을 Activity가 아닌 제한 시간과 종료 처리를 갖춘 서비스에서 관리해야 한다. 이는 이전 화면 중심 설계의 background 취소 조건을 이 새 경로에 맞추는 변경이며, UNKNOWN·사용자 취소·실패·제한 시간에 대한 종료 규칙은 유지한다. 3E 서비스에 반영했으며, 실제 제품에서 내비를 유지한 녹음·저장 경로를 확인했다. P/D 전환 중 지속·UNKNOWN 및 권한 상실 취소는 회귀 테스트와 관측 범위를 구분해 관리한다.

3A의 Room 저장은 Note·정책·AI job·후보 snapshot을 같은 트랜잭션으로 처리한다. 같은 음성 세션은 하나의 메모만 만들고, 원문은 수정하지 않는다. 방문이 없어도 저장하며 후보는 원래 날짜와 녹음 시각을 기준으로 고정한다. AI 제안과 사용자 확정은 조회 결과에서도 구분한다. 사진은 후속 데이터 계약만 있으며 스캔·사진 연결 기능은 아직 없다.

통합 기준 소스의 JVM 148개 통과 후 마지막 UI 수정에서는 영향 범위 17개를 다시 실행해 실패 0을 확인했다. 최종 Lint 오류 0·경고 26·힌트 1이며 제품·테스트 APK를 빌드했다. 실제 기기 통합 34개 중 최초 실행에서 Room 27개와 Compose 6개가 통과하고, 나머지 Compose 1개는 UNKNOWN 주입 전 초기 편집기 노드 부재로 실패했다. 같은 APK의 해당 메서드 분리 실행 1개와 관련 Compose 전체 7개 그룹 실행은 통과했다. 원인은 확정하지 못했으며 최초 실패 기록을 남긴다. 이는 앞선 검증 이력이다. 이후 게시 준비에서는 같은 제품 소스의 전체 JVM 155개 및 전체 기기 34개를 실행해 모두 통과했으며, 아래 게시 준비 기록에 산출물을 구분했다.

경고에는 기존 의존성 갱신 권고와 JNA native library의 16KB 정렬 문제가 포함된다. 현재 전용 Pleos AVD 실행은 확인했으나 모든 미래 16KB 기기 호환성을 주장하지 않는다. 실제 직접 메모 추가·수정과 앱 프로세스 재시작 뒤 수정 내용 유지, 시드 방문 3개 및 음성 원문 보존도 화면으로 확인했다.

3B 정책은 UNKNOWN에서 Locked, 주행 중 Driving으로 제한하고, 편집·공유는 PARKED에서만 허용한다. 새 음성 시작은 원안대로 DRIVING에서만 허용한다. 이는 신뢰된 차량 상태를 소비하는 순수 정책이며, 차량 API 값으로 신뢰성을 판정하는 어댑터는 아니다.

음성 세션은 15초에 캡처를 멈추고 시작 후 20초까지 최종 결과를 기다린다. 유효한 최종 결과를 받으면 원래 세션 ID·시각·원문 그대로 한 번 저장하며 방문이 없어도 저장 경로를 호출한다. 20초는 인식 결과의 도착 제한이므로 이미 수락한 저장은 더 늦게 끝날 수 있다. UNKNOWN·사용자 취소·호출자 취소를 처리하고, 일반 자원 정리 실패는 저장 결과와 구분한다. 취소가 저장 완료와 겹치면 실제로 커밋된 메모를 삭제하지 않는다. 실제 저장 종료 후 마이크 입력을 해제했고 주차 화면과 재실행을 확인했다. 파괴적인 플랫폼 서비스 강제 단절·모든 권한 조합을 실제 기기에서 재현했다는 의미는 아니다.

`allowBackup=false`와 두 형식의 백업 제외 규칙을 적용했고 APK에 포함된 규칙을 확인했다. 로컬 테스트 DB, 키·로컬 설정, APK·로그·화면 자료는 Git에 포함하지 않는다. 저장소의 Room schema JSON은 실제 사용자 DB가 아닌 구조 정의이며, 시드 방문과 테스트 문장은 합성 시연 데이터다.

## 안전 연동의 미해결 사항

상세 관측과 재현 절차는 [플랫폼 실측 기록](environment/mv-02-platform-spikes.md)에 있다.

- 현재 Pleos 이미지에서 주행용 Activity도 OS 차단 화면에 가려진다. 설치 출처 거부 기록이 있지만, 지원되는 개발 설치 절차는 추가 확인이 필요하다.
- 콘솔/browser 연결이 끊겨도 표준 차량 API가 정상값을 계속 반환한 관측은 유지한다. 다만 이를 실제 Car 서비스 단절과 동일시하는 공식 계약은 확인되지 않았다. 아래 사양 대조 결과에 따라 별도 DDS/browser 감시 기능을 필수 조건으로 추가하지 않는다.
- 제품의 실제 주행 상태 알림 버튼 → 오프라인 STT → 원문 저장 → 주차 표시·재실행은 확인했다. 일반 알림 패널 진입과 검증하지 않은 실패 시나리오는 별개다.
- 가상 기기의 네트워크 설정 복원과 실제 인터넷 재접속 여부는 구분해 확인해야 한다.

원안의 UNKNOWN 잠금·주행 중 편집/공유 제한·필수 음성 기능을 삭제하거나 완화하지 않는다. 알림·서비스 기반 음성 경로의 실측과 함께 UI·플랫폼 통합을 진행하되, 아직 검증하지 않은 항목을 완료로 표시하지 않는다.

2026-11-14 사양 재대조: 상세 계획 T1/T2와 v4 정정은 Car 서비스 lifecycle, 현재 UX 제한, 초기 기어·속도 수신과 유효성·일관성을 함께 확인하도록 요구한다. 원격 콘솔의 DDS/browser 연결을 별도 제품 입력으로 감시하라는 요구는 없다. 따라서 그 별도 API 확보를 구현의 절대 선행 조건으로 삼았던 해석은 정정한다.

**Ruling:** 차량 준비·단절은 승인된 AAOS Car API 경계에서 평가한다. 최초·재연결 시 UNKNOWN으로 시작하고 현재 연결의 UX·기어·속도가 모두 준비되어야 하며, 관찰 가능한 실패·단절·상태 충돌에서는 잠근다. 콘솔 종료를 실제 Car/VHAL 단절로 대신 판정하지 않는다. 이유는 원안의 복합 준비·실패 조건을 유지하면서 명시되지 않은 감시 기능을 추가하지 않기 때문이다. 판단이 틀렸을 때의 비용은 플랫폼이 정상값으로 계속 제공하는 상류 오류를 앱이 식별하지 못할 수 있다는 점이다. 이 한계를 기록하고 실제 서비스 실패 검증 공백을 남기며, 양산 차량 안전 인증을 주장하지 않는다.

## 코어 검증 재현

[README](../README.md)의 JDK 17·SDK 및 로컬 디렉터리 준비 후 실행한다. 프로젝트에서 제외된 파일을 복사할 필요는 없다.

```sh
./gradlew --no-daemon --console=plain testDebugUnitTest lintDebug assembleDebug assembleDebugAndroidTest
```

Room 검증에는 전용 새 AVD와 전용 ADB 서버를 사용한다. `MV_SERIAL`과 `MV_USER_ID`를 그 기기의 실제 값으로 설정하고, 앱과 테스트 APK를 **기존 앱이 없는 새 기기**에 설치한 뒤 아래 명령을 실행한다. 다른 프로젝트 기기에 덮어쓰거나 서명 충돌을 해결하려 기존 데이터를 삭제하지 않는다.

```sh
: "${MV_SERIAL:?전용 새 AVD serial을 설정하세요}"
: "${MV_USER_ID:?그 AVD의 실제 사용자 번호를 설정하세요}"
: "${ADB_SERVER_SOCKET:?전용 ADB 서버를 설정하세요}"
"$ANDROID_HOME/platform-tools/adb" -s "$MV_SERIAL" shell am instrument \
  --user "$MV_USER_ID" -w -r \
  -e class app.memoryvault.data.VisitDaoTest,app.memoryvault.data.MemoryRepositoryTest,app.memoryvault.data.AiLinkQueueTest,app.memoryvault.data.MemoryPersistenceTest,app.memoryvault.data.NotePresentationTest \
  app.memoryvault.test/androidx.test.runner.AndroidJUnitRunner
```

`am` 명령의 exit code만 확인하지 않고 `OK (27 tests)`와 개별 실패 유무를 확인한다. 테스트는 in-memory DB 또는 자신이 만든 `mv03a-test-<UUID>.db`만 사용·정리한다. 마이크·차량 정책·네트워크 설정을 바꾸는 테스트가 아니다.

## Git 운영 기준

2026-11-14 사용자 정정에 따라 이전 계획의 develop 중심 운영 대신 아래 흐름을 따른다.

1. 검증된 최신 `main`에서 작업 브랜치를 만든다.
2. 해당 기능의 구현·검증·독립 검토가 끝나면 `main`에 병합한다.
3. 릴리즈 완료 기준을 충족한 경우에만 그 커밋에서 릴리즈 브랜치와 버전 태그를 만든다.
4. 원격 push 전에는 feature/main/릴리즈의 정확한 파일·이력·커밋 범위를 보여 주고 사용자 확인을 받는다.

현재 완료 기준선은 2단계 `0c5383d`다. 미완료 3단계의 진행분은 `feature/03-offline-memory`에 보존하고, `main`에 완료된 기능처럼 병합하거나 릴리즈로 표시하지 않는다. 기존 develop과 작업 브랜치는 임의로 삭제하지 않는다. 3단계 전체 완료 판정에는 남은 일반 알림 진입 조건 처리가 필요하며, 4단계는 별도 진행 지시 없이 시작하지 않는다.

## UI 작업 시점 정정 — 2026-11-14

사용자 지시에 따라 3단계는 버튼 녹음 → 원문 저장 → 주차 후 하루 초안에서 저장 메모 표시 → 재실행 복원의 최소 흐름을 우선 완성한다. 메모 표시는 검색 기능 추가를 뜻하지 않으며, 주행 중에는 원문 없이 상태만 표시한다.

3~6단계에서는 기능 사용·확인에 필요한 최소 화면과 가독성·접근성·안전 상태 표시를 구현한다. 최신 사용자 정정에 따라 **5·6단계를 병렬 개발하고 전체 UI 다듬기는 후속 P2의3D 기억 맵 작업 때 함께 진행**를 진행한다. 이전 5→UI→6 순서는 대체됐다. 기존 OpenAI 범위는 유지한다. Gleo 시작은 계속 후속 구현이다. 중간 검증은 변경·직접 영향·필수 안전 회귀에 집중하고, 전체 필수 통합 검증은 3단계 마무리에 수행한다. 각 단계 완료 후 보고하고 중단하며, 다음 단계는 명시적 진행 지시 후 착수한다.

### 차량 상태 전달 순서 처리 — 3E 구현

실제 P↔D 전환에서는 유효한 기어와 UX 제한 콜백이 서로 다른 순서로 도착했다. 같은 연결에서 이미 신뢰된 상태를 확인한 뒤 발생한 제한된 조합에만 최대 500ms `TRANSITION`을 사용한다. 이 상태에서 새 녹음·편집·공유는 잠그고, 이미 수락한 녹음만 기존 15초/20초 제한 내에서 유지한다. 오류·누락·단절·잘못된 값·시작/재연결은 즉시 UNKNOWN이며 녹음을 취소한다. 반복 콜백으로 유예를 늘리지 않는다. 500ms는 실측 보장값이 아닌 구현 상한으로, 유효한 값의 지속적 충돌에서도 기존 녹음이 그 시간만큼 이어질 수 있다는 한계가 있다.

### 클론 검증 정책 정정 — 2026-11-14

독립 클론 검증은 사용자가 별도로 명시적으로 요청할 때만 수행한다. 단계·feature 완료나 push의 기본 필수 조건으로 두지 않는다. 기존에 완료된 검증 기록은 사실로 보존하며 반복하지 않는다. 제품 APK 빌드, 실제 기기 시험, 필요한 안전·비밀정보 점검은 유지한다.

### 정상 알림 진입 — 사용자 결정

사용자는 개발 명령으로만 알림창을 여는 데모를 3단계 완료로 수락하지 않고, **3단계 완료를 보류하며 일반 진입 경로를 계속 해결**하도록 지시했다. 현재 구현·음성/직접 메모 저장·복원 증거는 보존하며, 문서의 상태 메뉴 설명과 실제 에뮬레이터 UI를 대조하는 후속 작업을 진행한다. 주행 제한 우회, 시스템 앱 교체, 권한 확장 또는 외부 문의는 이 결정만으로 자동 실행하지 않는다.

후속 확인 결과: 현재 P0 화면의 상태 표시줄 아래로 끌기·시각 영역 클릭은 반응이 없었고, Android14 공개 소스의 Meta+N 조합도 이 이미지에서 열기 동작을 관측하지 못했다. 이는 모든 가능한 진입 조작이 없다는 증명은 아니다. StatusBar disable 플래그 0, 사용자0/10 초기 설정 완료1을 읽었으며 설정은 변경하지 않았다. 공식 Pleos Status bar 도식의 알림센터는 Door Lock·Search 뒤 SP0의 종 아이콘인데 현재 화면에서는 식별하지 못했다. 공식 배포 XML과 릴리스 노트의 최신 확인 버전도 v2.1.0이므로 근거 없는 이미지 재설치를 하지 않는다.

남은 외부 확인 사항은 **v2.1.0 일반 설치 앱의 알림센터를 사용자가 여는 정확한 버튼/제스처와 종 아이콘 표시 조건**이다. 공식 지원 안내 또는 지원되는 이미지에서 정상 진입 증거를 확보하기 전에는 3단계 전체 완료·릴리즈로 표시하지 않는다. 당시 main 병합도 보류했으며, 이후 미완료 체크포인트 게시 요청과 승인 차단 상태는 아래 최신 기록을 따른다. 제품 기능 수락 증거와 실행 가능한 APK는 유지한다.

## 공동 인수인계 게시 준비 — 2026-11-14

일반 알림센터 진입 문제를 [GitHub 이슈 #1](https://github.com/chowonbhin/Pleos/issues/1)로 등록했다. 공식 문의 메일은 사용자가 발송하지 않고 내용만 보관하도록 결정해 발송하지 않았다.

사용자가 사이드 채팅의 문서와 현재 구현을 함께 main에 push하고 다음 담당자의 테스트 절차를 인수인계하도록 요청했다. 로컬 origin/main 기준은 `0c5383d`로 확인했다. 자동 승인 검토가 앞선 ‘3단계 완료 후 병합’ 조건과 현재 미완료 상태를 이유로 main 병합을 차단했으므로, main을 변경하지 않고 feature에서 문서를 통합·검증하고 있다. 정확한 전송 범위가 준비된 후 미완료 사항을 명시한 체크포인트의 main 게시 승인을 확인한다. 이 게시 요청을 3단계 완료·릴리즈·4단계 착수로 해석하지 않는다.
